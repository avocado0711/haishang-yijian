# 架构、数据来源与业务闭环

## 系统分层

```text
Client Component
  需求访谈 / 确认状态 / 资源选择 / 版型与打样 / 台账导出
        |
Route Handlers
  /api/chat   需求解构与回退
  /api/design 提示词与图像适配
  /api/handoff 完整台账落盘
        |
Adapters
  DeepSeek Chat Completions
  OpenAI-compatible Image Generations
  Static enterprise asset fallback
```

## 数据来源

- 版型、面料、工艺、案例、款式图和打样图：`src/lib/brief.ts` 与 `public/assets/` 中的模拟静态企业档案。
- 需求对话：DeepSeek；网络或模型异常时使用可继续操作的本地规则归纳。
- 图像：配置了 `IMAGE_API_BASE_URL` 时调用图像服务，否则使用企业静态方案图。
- 交接：前端生成完整 `HandoffPackage`，服务端校验后写入 `data/handoffs/{id}.json`。

## 业务闭环

1. 业务人员选择高端私定或团体职业服，进入客户访谈。
2. 对话字段按场景与规模、轮廓与比例、领型与纹样、面料与色彩、活动与体感、禁忌与边界六个维度归纳，并区分「已确认」与「待确认」。
3. 进入设计前必须同时满足两个条件：品类已确认，且至少 3 个设计相关字段已确认。未确认内容不能作为最终设计要求。
4. 系统按品类、工作模式、场景、风格、面料和活动需求匹配企业资源；品类先从自然语言映射到资源家族，再在家族内排序。
5. 版型默认值、面料候选、打样检查项和最终产品名称均从确认需求派生，并生成带来源标注的方案初稿。
6. 视觉提示词拆分为成衣效果、工艺细节和上身穿搭三套，只使用确认字段；企业资产与面料候选单独标注为参考，可复制、导出和随台账归档。
7. 业务人员填写业务台账备注、补全打样检查并生成交接台账；模式切换、载入案例和新建方案前均有破坏性操作确认。
8. 台账记录六维需求、方案初稿、三套提示词、检查结果和操作留痕，交由人工复核。

## 关键一致性规则

- 品类是资源匹配硬约束，外套需求不会落到衬衫或礼服基线；没有同品类资源时返回明确缺口，不回退到默认资产，也禁止导出跨品类台账。
- 工作模式是资源池硬约束，私定与团体职业服使用不同资源候选。
- 设计门槛要求已确认品类 + 至少 3 个设计相关字段；体型、人群、数量、排除项等非设计字段不能单独解锁设计页。
- 领型和衣长从确认需求派生到版型与打样检查。
- 视觉提示词拒绝 `待定`、`待确认`、`建议` 等未确认措辞，也不自动补写未确认的领型、面料和色彩。
- 交接包使用资源快照而非仅保存资源 ID，避免资源后续变更造成历史记录漂移。

## 失败与降级

| 失败 | 处理 |
| --- | --- |
| DeepSeek 超时或返回异常 | 自动重试一次；仍失败则返回本地结构化归纳，并允许一键恢复在线模型 |
| 图像服务未配置或失败 | 保留企业静态资产图，同时继续提供完整提示词 |
| 当前品类没有同品类企业资产 | 停止推荐和阶段推进，展示明确缺口；不跨品类兜底，禁止导出伪基线台账 |
| 重复提交 | 提交按钮进入 loading 并禁用 |
| 错误选择导致字段冲突 | 重新进入设计或版型时按确认需求重新派生 |

## 后续落地路径

1. 将模拟资产迁移至集团资产库，保留标签、版本与适用规范。
2. 接入业务台账、企微通知和权限系统，不直接接入生产下单。
3. 用真实脱敏案例校准匹配规则和六维需求词典。
4. 建立人工确认记录、模型版本、提示词版本与资源使用审计。
